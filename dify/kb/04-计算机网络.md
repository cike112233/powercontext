## TCP 连接与可靠性

### Q: 三次握手为什么是三次，两次不行、四次没必要？
- 领域: 网络
- 难度: 中级
- 考察点: 同步序列号与防历史连接
- 参考答案要点: 三次用于双向确认通道并同步 ISN；两次会被网络滞留的旧 SYN 在服务端凭空建起半开连接；拆成四次只多一个 RTT 没收益；Linux 的 ISN 按 RFC 6525 由每 4 毫秒递增的时钟加四元组哈希生成，防历史连接与猜序号；队列分半连接（`tcp_max_syn_backlog`）与全连接（取 `min(backlog, somaxconn)`，5.4 起 somaxconn 从 128 升到 4096），全连接溢出默认丢弃 SYN-ACK 靠客户端退避重传
- 追问: 全连接队列溢出时客户端看到什么现象？；SYN cookies 为什么能绕过半连接队列？
- 评分标尺: 及格=说清同步 ISN 与防旧连接；良好=给两层队列与 somaxconn 默认值；优秀=能讲 ISN 算法与 syncookies 代价
- 常见误区: 解释成确认三次才可靠；以为 backlog 只有一层队列

### Q: 四次挥手顺序是什么，TIME_WAIT 为什么等 2MSL？
- 领域: 网络
- 难度: 高级
- 考察点: 主动关闭方状态机与端口资源后果
- 参考答案要点: 四包是 FIN、ACK、FIN、ACK，被动方收 FIN 时可能还有数据待发故不能合并；主动方进 TIME_WAIT 等 2MSL，Linux 的 MSL 硬编码 30 秒所以是 60 秒；两个目的是应答可能丢失的末个 ACK，并让旧报文在网络中消亡；危害是占住四元组，客户端短连接高频时本地端口耗尽，`ip_local_port_range` 默认约 32768~60999；治本是长连接与连接池，`tcp_fin_timeout` 管的是 FIN_WAIT_2 不是 TIME_WAIT，`tcp_tw_recycle` 因 NAT 误丢包已在 4.12 移除
- 追问: 为什么进 TIME_WAIT 的是主动关闭方？；几十万 TIME_WAIT 你按什么顺序调优？
- 评分标尺: 及格=四步与两个目的；良好=给 MSL=30 秒与端口范围；优秀=纠正 fin_timeout 误解并提 `tcp_tw_reuse` 只对出站有效
- 常见误区: 把 2MSL 说成等对方收完数据；建议开 tcp_tw_recycle

### Q: TCP 和 UDP 怎么选，什么场景必须用 UDP？
- 领域: 网络
- 难度: 中级
- 考察点: 从机制差异推出选型
- 参考答案要点: TCP 给有序无重复的字节流，代价是连接状态、握手 RTT、队头阻塞（丢一段整条流等重传）与拥塞控制主动降速；UDP 保留消息边界、首部只 8 字节（TCP 最少 20）、无连接无重传，但路径 MTU 常 1500 字节、分片丢一片等于整包丢；必须用 UDP 的理由：延迟敏感可容忍丢包（实时音视频、游戏状态同步）、组播只有 UDP、要避免队头阻塞（DNS、QUIC）；数据必须完整有序就选 TCP；折中是 KCP、QUIC 这类在 UDP 上重建可靠传输
- 追问: 用 UDP 做可靠业务至少要补上哪几件事？；UDP 分片为什么危险，怎么避免？
- 评分标尺: 及格=列首部、连接、有序性差异；良好=给两条必须用 UDP 的硬理由；优秀=能谈分片风险、MTU 约束与 KCP 折中
- 常见误区: 说 UDP 一定比 TCP 快；认为 UDP 无法可靠；把粘包算成 UDP 问题

### Q: TCP 靠什么保证不丢不乱不重复，序号和确认号怎么配合？
- 领域: 网络
- 难度: 高级
- 考察点: 序号语义、ACK 类型与重传定时器
- 参考答案要点: 序号按字节编号（SYN 与 FIN 各占一号），确认号是期望的下一字节即累计确认，乱序由接收方重排、重复按序号丢弃；两条丢包检测路：RTO 取 `SRTT + 4 * RTTVAR`，Linux 下限 200 毫秒、初始 1 秒、上限 120 秒并指数退避，`tcp_retries2` 默认 15 次约十几分钟放弃；收到 3 个重复 ACK 走快速重传不等 RTO；SACK 让接收方报告非连续已收块避免空洞重传；可发字节取 rwnd 与 cwnd 较小值；`tcp_keepalive_time` 默认 7200 秒太长，故应用层自己发心跳
- 追问: 累计确认为什么浪费重传信息，SACK 补了什么？；快速重传的 3 个 dupACK 阈值怎么来的？
- 评分标尺: 及格=讲序号加累计确认加重传；良好=区分两种重传并给 RTO 边界与 keepalive 默认值；优秀=能解释 SACK 与 rwnd/cwnd 取小
- 常见误区: 认为每段都要一个 ACK；把滑动窗口只当拥塞控制

### Q: 拥塞控制四个阶段讲一下，慢启动阈值怎么起作用？
- 领域: 网络
- 难度: 高级
- 考察点: 窗口随反馈变化的算法与默认参数
- 参考答案要点: 慢启动不慢，是每个 RTT 让 cwnd 翻倍的指数增长，用来快速试探带宽；cwnd 到 `ssthresh` 转拥塞避免，改为每 RTT 只加 1 个 MSS 的线性增长；Linux 新建连接 ssthresh 初始近似无穷大，通常首次丢包才设成约 cwnd 一半；初始窗口默认 10 个 MSS（RFC 6928 的 IW10），对首屏这类小传输影响很大；3 个重复 ACK 走快速重传与快速恢复（ssthresh 减半、cwnd 约 ssthresh 加 3），超时则 cwnd 回 1 重新慢启动；Linux 默认 CUBIC 靠丢包判拥塞易受大缓冲影响，BBR 改用 RTT 与带宽估计
- 追问: ssthresh 何时被更新，为什么超时比三个 dupACK 更重？；小文件传输为什么调初始窗口比换算法划算？
- 评分标尺: 及格=四阶段与指数转线性；良好=给 ssthresh 减半、IW10、超时回 1；优秀=能比较 Reno、CUBIC、BBR 的信号来源与副作用
- 常见误区: 把慢启动说成速度慢；以为 ssthresh 是固定配置项

### Q: Nagle 算法是什么，为什么我的请求偶发 40 毫秒延迟？
- 领域: 网络
- 难度: 高级
- 考察点: 两个默认优化互相等待的症状
- 参考答案要点: Nagle 规则是有已发未确认数据时新数据要攒够一个 MSS 或等 ACK 才发，为消除小包首部开销；对端默认还开延迟确认，最多等 `TCP_DELACK_MAX` 40 毫秒或搭下一个包回 ACK；两者咬合就死锁：客户端等 ACK 才发下一段、服务端等下一段才顺带 ACK，每对小往返固定卡约 40 毫秒；典型触发是一条消息分两次 write 或先发探测小包；处理是请求响应型协议设 `TCP_NODELAY`（Linux 默认开着 Nagle 要显式关）并合并小包为一次 write 或 writev；`TCP_QUICKACK` 只是临时关延迟确认，内核会自行恢复
- 追问: 为什么 Nagle 与 delayed ACK 单独开都没问题？；除了分两次 write 还有哪些写法会踩坑？
- 评分标尺: 及格=说 Nagle 攒包与 40 毫秒来自 delayed ACK；良好=给 TCP_DELACK_MAX 与 TCP_NODELAY 默认状态；优秀=能讲 QUICKACK 非持久
- 常见误区: 把 40 毫秒归给 TIME_WAIT；以为 TCP_NODELAY 默认开启

## HTTP 与安全

### Q: HTTP/1.1、2、3 各解决什么，队头阻塞在哪一层？
- 领域: 网络
- 难度: 高级
- 考察点: 区分连接复用与队头阻塞的层次
- 参考答案要点: HTTP/1.1 有 keep-alive 与 chunked，但一条连接同时只跑一个请求响应，浏览器对单域名限约 6 条，管线化因响应须按序而废弃，这是应用层队头阻塞；HTTP/2 用二进制分帧与流 ID 在单条 TCP 上多路复用，解决应用层阻塞，另有 HPACK 头压缩、`MAX_CONCURRENT_STREAMS`（Nginx 默认 128）、初始流控窗口 65535 字节，但所有流共用一个字节流，丢一段就阻塞全部流，TCP 层队头阻塞仍在；HTTP/3 用 UDP 上的 QUIC，每流独立重传、TLS1.3 内置 1-RTT、可 0-RTT、按 Connection ID 迁移
- 追问: H2 与 H1 的队头阻塞分别在哪一层？；几十个静态资源时 H2 的收益主要来自哪里？
- 评分标尺: 及格=说出 keep-alive、多路复用、QUIC；良好=明确 H2 保留 TCP 层阻塞；优秀=给并发流上限、HPACK、0-RTT 与迁移
- 常见误区: 说 HTTP/2 彻底解决队头阻塞；把 QUIC 当 UDP 版 TCP

### Q: HTTPS 握手做了什么，性能代价在哪，怎么降？
- 领域: 网络
- 难度: 高级
- 考察点: 握手消息序列与真实开销来源
- 参考答案要点: TLS1.2 需 2 个 RTT：ClientHello 带随机数与套件，ServerHello 回证书链、ServerKeyExchange（ECDHE 公钥加签名）与 HelloDone，客户端回 ClientKeyExchange 与 Finished，服务端再 Finished；TLS1.3 砍到 1 个 RTT，ClientHello 直接带 key_share 预猜曲线并删掉静态 RSA 交换与弱套件，PSK 配 newSessionTicket 支持 0-RTT 但有重放风险；代价三块：额外 RTT、证书链验签的非对称运算（RSA-2048 私钥签约几十到几百微秒，ECDSA P-256 更快且证书更小）、对称加解密（AES-GCM 有 AES-NI 时单核数 GB/s 可忽略）；降成本用 TLS1.3、会话恢复、OCSP stapling、LB 卸载
- 追问: TLS1.3 靠什么做到 1-RTT，猜曲线会不会浪费？；0-RTT 的重放风险具体是什么？
- 评分标尺: 及格=说密钥交换、身份验证与 Finished 校验；良好=给出 1.2 是 2RTT、1.3 是 1RTT；优秀=能拆三块成本并给 stapling 对策
- 常见误区: 说 HTTPS 慢只是因为有加密；混淆 TLS 与 SSL 版本

### Q: 为什么 HTTPS 要对称加密和非对称加密混着用？
- 领域: 网络
- 难度: 中级
- 考察点: 两者各补什么短板与前向保密
- 参考答案要点: 非对称解决无预共享密钥时怎么安全协商密钥，但大数运算慢几个数量级且单次加密长度受限（RSA-2048 约 245 字节），用它加密整段流量不现实；对称（AES-GCM 有 AES-NI 时单核数 GB/s 且自带认证标签）快但要求双方先有同一把密钥；于是非对称或 DH 只用来确立会话密钥，数据全走对称 AEAD；TLS1.3 实际用 ECDHE 临时密钥对而不是公钥加密密钥，这带来前向保密，日后私钥泄露也解不开历史流量，kRSA 无此性质故被删除；证书公钥此时只用于签名握手做身份认证
- 追问: ECDHE 与 RSA 密钥交换在前向保密上差在哪？；TLS1.3 里证书公钥到底用来干什么？
- 评分标尺: 及格=说非对称换密钥、对称传数据；良好=给出性能与长度限制的原因；优秀=能讲 PFS、认证与加密职责分离及 AEAD 动机
- 常见误区: 说用非对称加密业务数据；认为 HTTPS 全程 RSA 加密内容

### Q: TLS 证书链怎么验证，中间人在什么条件下能成功？
- 领域: 网络
- 难度: 高级
- 考察点: 信任锚、链式签名与真实攻击面
- 参考答案要点: 证书是公钥加主体加有效期再由上级 CA 私钥签名的 X.509 v3 结构；验证从叶子逐级向上验签，最后必须落在本地信任库中的自签根，服务器要下发叶子加全部中间证书，只发叶子会让部分客户端建不了链；除验签还要校域名（看 SAN，通配符只允许最左一级）、有效期、用途扩展与吊销状态（CRL 慢、OCSP 少用，现走 stapling）；中间人成立的前提是攻击者的证书被信任：企业让员工装自签根做 TLS 审计、CA 误签（DigiNotar）、用户被骗装根、或协议被降级；防御有证书固定、HSTS（max-age 常设 31536000）、CT 日志与 TLS1.3
- 追问: 为什么根证书必须在本地，验证到哪一步停？；只发叶子证书为什么有的客户端不报错？
- 评分标尺: 及格=说清逐级验签止于本地信任锚；良好=补 SAN、有效期、吊销与 fullchain；优秀=能讲 pinning、HSTS、CT 与装根即被 MITM
- 常见误区: 认为有 HTTPS 就绝对安全；把证书当成只用于加密

## DNS 与整体链路

### Q: 域名是怎么一步步解析出 IP 的，TTL 起什么作用？
- 领域: 网络
- 难度: 中级
- 考察点: 完整解析路径、缓存层级与 TTL 语义
- 参考答案要点: 顺序是浏览器缓存、`getaddrinfo`、`/etc/hosts`（优先级由 `nsswitch.conf` 的 files dns 决定）、系统或 resolved 缓存、递归解析器；递归器替客户端迭代：问根（13 组任播）得 .com 的 TLD，问 TLD 得权威 NS，问权威得 A 或 AAAA；默认 UDP 53，响应超 512 字节（无 EDNS0）或 zone 传输改 TCP；TTL 是权威给下游的缓存秒数，各级独立过期且不能提前收回，所以切指向会在旧 TTL 内出现部分用户打老机器，实践先降到 300 秒再切；Java 另有一层 `networkaddress.cache.ttl`（无 SecurityManager 时约 30 秒、负向 10 秒）
- 追问: TTL 从 3600 改成 60 什么时候才生效？；Java 服务为什么要单独设 networkaddress.cache.ttl？
- 评分标尺: 及格=讲出缓存层级与迭代三步；良好=说明 TTL 由权威定且各级独立过期；优秀=能提 hosts 优先级、Java 缓存与 Happy Eyeballs
- 常见误区: 认为 DNS 一定走 TCP；说 TTL 可强制立即生效；搞反 hosts 与 DNS 优先级

### Q: DNS 污染是怎么回事，有什么防护手段？
- 领域: 网络
- 难度: 中级
- 考察点: 明文 UDP 解析可被抢先伪造与加密代价
- 参考答案要点: 传统 DNS 是明文 UDP，响应可被中间设备观察并伪造，攻击者只要猜中 16 位事务 ID 并赶在真答案前送达就能投毒，源端口随机化是主要防线；也有注册商或中间盒把非法域名直接解析到广告 IP；拿到假 IP 后 HTTPS 通常因证书主体不符而报警，但配合假根证书或降级就能骗过；防护是 DNSSEC 给记录加 RRSIG 并链到根做真实性校验（验真不加密）、DoT 用 853 端口、DoH 走 443 复用 HTTPS（能绕开企业 DNS 但也让运维难审计）、App 侧可用 HTTPDNS 按 IP 请求并带 Host 头；hosts 文件可覆盖本地解析结果
- 追问: DNSSEC 能防污染为什么不顺便加密？；DoH 相比传统 DNS 还有什么副作用？
- 评分标尺: 及格=说清明文 UDP 可被抢先；良好=给 16 位 ID 与端口随机化；优秀=能区分 DNSSEC 验真与 DoH 保密并讲 HTTPDNS
- 常见误区: 以为有 HTTPS 就不怕 DNS 造假；把 DNSSEC 当成加密手段

### Q: 从输入 URL 到页面出现经历哪些阶段，哪些最容易慢？
- 领域: 网络
- 难度: 中级
- 考察点: 完整链路视图与瓶颈定位
- 参考答案要点: 阶段是 DNS、TCP 握手（1 RTT）、TLS（1.2 是 2 RTT、1.3 是 1 RTT）、请求、服务端排队与处理、响应传输（受初始窗口约 10 个 MSS 约束）、浏览器解析建 DOM 与 CSSOM 后首次渲染；CSS 是渲染阻塞资源、同步 script 阻塞解析，defer 保持顺序、async 不等；最慢处常在跨地域 RTT 与握手（首字节前无法并行）、服务端连接池或线程池排队与 GC 停顿、首屏体积（100KB 在 IW10 下要多轮往返）、多余的重定向（一个 301 就是一整轮）；优化顺序是 CDN 就近、H2 或 H3、长连接与连接池、压缩与关键 CSS 内联、preconnect
- 追问: TTFB 包含哪几段，怎么拆开测？；初始拥塞窗口为什么会限制首屏大小？
- 评分标尺: 及格=按顺序说 DNS、TCP、TLS、请求、渲染；良好=指出 CSS 与 JS 阻塞；优秀=能把 IW10、重定向、TTFB 分解对上优化
- 常见误区: 说拿到 HTML 才开始建连接；把所有慢都归给带宽

### Q: 状态码怎么分族，301、302、502、504 分别是谁的问题？
- 领域: 网络
- 难度: 中级
- 考察点: 从状态码定位问题层级与责任方
- 参考答案要点: 1xx 信息（101 升级 WebSocket）、2xx 成功（204 无 body、206 Range 续传）、3xx 重定向、4xx 客户端错（401 未认证、403 无权限、408 客户端太慢、413 体过大、429 限流）、5xx 服务端错；301 永久且会被浏览器与搜索引擎缓存、改错难回滚，302 临时且历史上可把 POST 变 GET，307 与 308 要求保持方法，304 是缓存协商不是跳转；502 是反代从上游拿到无效响应（进程挂、连不上、返回不是合法 HTTP），504 是等上游超时（Nginx `proxy_read_timeout` 默认 60 秒）；口诀是 502 上游坏了、504 上游太慢；伴随 premature closed 多是 LB 空闲超时小于上游 keep-alive 超时
- 追问: 网关持续报 504 你按什么顺序查？；301 被浏览器缓存之后怎么救？
- 评分标尺: 及格=说清五族与四码；良好=准确区分 502 与 504 的上游表现；优秀=能讲超时错配与 proxy_read_timeout 默认值
- 常见误区: 把 502 说成服务超时；认为 401 与 403 等价；用 301 做临时灰度

## 跨域、负载与传输细节

### Q: 跨域怎么产生的，CORS 预检什么时候会发？
- 领域: 网络
- 难度: 中级
- 考察点: 同源策略、预检条件与凭证规则
- 参考答案要点: 同源指协议、域名、端口三者一致，浏览器只拦截跨源响应的读取，请求本身已发出所以副作用仍会发生，CSRF 是另一回事；许可靠 `Access-Control-Allow-Origin`、`Allow-Methods`、`Allow-Headers`、`Expose-Headers`、`Allow-Credentials`、`Max-Age`；简单请求需方法为 GET、HEAD 或 POST，`Content-Type` 只在 form-urlencoded、multipart、text/plain 内且无自定义头，否则先发 OPTIONS 预检，`Max-Age` 可让浏览器缓存结果（未指定约 5 秒，设 86400 大幅减 OPTIONS）；带凭证时 Allow-Origin 不能是 `*` 且要 `Allow-Credentials: true`，Cookie 还需 SameSite=None 配 Secure；Nginx 的 add_header 默认不作用于 4xx、5xx，要加 always
- 追问: 预检失败时后端日志里能看到什么？；为什么 401 响应也必须带 CORS 头？
- 评分标尺: 及格=说同源三要素与关键响应头；良好=列简单请求完整条件与 Max-Age；优秀=能讲凭证与 `*` 互斥、SameSite、add_header always
- 常见误区: 认为跨域时请求不发出去；把 CORS 当安全手段；以为 Allow-Credentials 可配 `*`

### Q: 四层负载和七层负载差别在哪，会话保持怎么做？
- 领域: 网络
- 难度: 高级
- 考察点: 转发依据、成本与有状态归属
- 参考答案要点: 四层按 IP 加端口转发、不解析应用报文，典型 LVS 有 NAT、DR（响应由后端直回客户端故吞吐最高，需同二层网段）、FULLNAT，PPS 高且不必卸载 TLS，但拿不到 URL 与 Cookie 就无法按内容路由或重试；七层解析 HTTP（Nginx、Envoy），可按 host、path、header、SNI 路由，能做 TLS 卸载（吃 CPU）、灰度、限流与后端连接复用（Nginx upstream keepalive 默认关闭，要配 `keepalive 32` 加 `proxy_http_version 1.1` 并清空 Connection 头）；算法有轮询、加权、least-conn（耗时差异大时更好）、ip_hash（NAT 后同 IP 大量用户会倾斜）、一致性哈希加虚拟节点（扩缩容只迁约 1/N）；会话保持首选无状态化配 Redis 或 JWT，植入 SRV 这类粘性会在后端下线时丢会话
- 追问: LVS 的 DR 模式为什么吞吐最高，前提是什么？；ip_hash 在什么网络下明显不均？；会话进 Redis 后还有哪些隐式粘在机器上的状态？
- 评分标尺: 及格=说 L4 看四元组、L7 看 HTTP；良好=给 ip_hash 倾斜与 upstream keepalive 需显式开；优秀=能比 TLS 卸载成本并指出隐式状态
- 常见误区: 认为 L4 做不了健康检查；把粘性当唯一方案；以为 Nginx 后端默认复用连接

### Q: QUIC 自己实现可靠传输，为什么还要建在 UDP 上？
- 领域: 网络
- 难度: 高级
- 考察点: 内核 TCP 的不可演进性与 QUIC 收益
- 参考答案要点: 首要原因是可部署：TCP 在内核协议栈里，改进要等系统升级，中间盒还常按 TCP 语义干预并封杀新扩展，放进用户态的 UDP 能由库自己发版；机制收益是每条 stream 独立可靠交付、按包号而非字节流重传，丢包只阻塞所在流，解决 TCP 层队头阻塞；连接由 Connection ID 标识而非四元组，换 Wi-Fi 到蜂窝或 NAT 重启都能迁移；TLS1.3 内置、首次 1-RTT、PSK 可 0-RTT；代价是用户态收发靠 sendmmsg 与 GSO、CPU 与切换开销高，UDP 可能被限速丢弃故要留 alt-svc 回退 TCP，最小包 1200 字节且超 MTU 会整包丢
- 追问: 为什么 TCP 上的队头阻塞在 HTTP/2 里绕不开？；QUIC 的连接迁移在 NAT 后怎么工作？；UDP 的 CPU 代价你打算怎么补？
- 评分标尺: 及格=知避免队头阻塞与内核改不动；良好=讲包号、每流独立、Connection ID、0-RTT；优秀=能谈用户态开销与 UDP 被限速的回退
- 常见误区: 说用 UDP 所以不可靠；认为 QUIC 不需要拥塞控制

### Q: TCP 粘包拆包是怎么回事，为什么首选长度前缀？
- 领域: 网络
- 难度: 中级
- 考察点: 字节流语义与帧化的工程取舍
- 参考答案要点: 根因是 TCP 为无消息边界的字节流，一次 write 不保证对应一个段（Nagle 合并小写、MSS 拆大写、窗口不足或 read 太小都只交付一部分），所以要应用层帧化，UDP 有边界无此问题；三种做法是定长（浪费带宽要填充）、分隔符（HTTP 头 CRLF、Redis RESP，正文含分隔符得转义）、长度前缀（写本帧字节数、读够才解析）；长度前缀要明确字段宽度与字节序（网络序大端，Java ByteBuffer 默认大端、Go 用 binary.BigEndian），用 4 字节避免 65535 上限，必须设最大帧长（如 8MB）超限即断，未收全要留在缓冲区；Netty 的 LengthFieldBasedFrameDecoder 最常错的是 length 指整帧还是 body，对应 lengthAdjustment 与 initialBytesToStrip
- 追问: 用 2 字节长度字段会踩什么坑？；length 指整帧还是 body，Netty 参数怎么填？
- 评分标尺: 及格=说清字节流无边界；良好=给三方案对比与大端、4 字节；优秀=能讲半包缓存、lengthAdjustment 与恶意帧防御
- 常见误区: 认为粘包是 TCP 缺陷；用固定 read 大小当分帧依据

### Q: 接收窗口降到 0 之后会发生什么，窗口字段不够用怎么办？
- 领域: 网络
- 难度: 高级
- 考察点: rwnd 通告、零窗探测与窗口缩放
- 参考答案要点: 接收方在每个 ACK 首部通告 rwnd，发送方可发字节取 rwnd 与 cwnd 较小值；rwnd 为 0 时停发普通数据并启动零窗探测定时器（Linux 复用 RTO 指数退避），定期发 1 字节探测包，ACK 带回非零窗口即恢复，此机制为避免窗口更新丢失造成双方永久互等；双方都要防 silly window syndrome，接收侧要等可用缓冲恢复到至少 min(MSS, 缓冲一半) 才通告；窗口字段只有 16 位即上限 65535 字节，按 BDP 算远不够，靠窗口缩放（RFC 7323，移位 0~14、最大约 1GB），只能在 SYN 协商；`net.ipv4.tcp_rmem` 默认 4096、131072、6291456，手工设 SO_RCVBUF 会关掉自动调优；抓包大量 Zero Window 多是应用读得慢、线程池满或 GC 停顿
- 追问: 窗口更新包丢了靠什么恢复，为什么探测只发 1 字节？；手工调大 SO_RCVBUF 为什么可能更差？
- 评分标尺: 及格=说 rwnd 通告与零窗探测；良好=给 1 字节探测、min(MSS, 半缓冲) 与缩放移位；优秀=能用 tcp_rmem 默认值与抓包症状排障
- 常见误区: 把接收窗口当拥塞窗口；认为窗口为 0 就是断连；把零窗当 TCP 的 bug
