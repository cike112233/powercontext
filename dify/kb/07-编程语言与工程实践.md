## Java 虚拟机与并发

### Q: JVM 运行时内存分成哪几块，哪些情况会 OOM？
- 领域: 语言
- 难度: 中级
- 考察点: 运行时数据区划分与各自的溢出场景
- 参考答案要点: 线程私有：虚拟机栈（-Xss 默认 1MB，深递归抛 StackOverflowError、线程过多抛 OOM）、程序计数器（唯一不 OOM）、本地方法栈；线程共享：堆（JDK8 起字符串常量池与静态变量也在堆内）与方法区（Metaspace 用本地内存存类元信息，-XX:MaxMetaspaceSize 默认无上限，CGLIB/动态代理类暴涨就 Metaspace OOM）；另有堆外 DirectByteBuffer 受 -XX:MaxDirectMemorySize 限制且 jmap 看不见；对象头 = Mark Word 8 字节 + 压缩类型指针 4 字节 + 8 字节对齐
- 追问: Metaspace 持续增长怎么定位？堆外内存泄漏用什么工具确认？
- 评分标尺: 及格=堆/栈/方法区三块齐全；良好=补上 Metaspace 取代永久代与堆外内存；优秀=能讲 Mark Word 与线程数×栈大小的内存挤压
- 常见误区: 还在说永久代和 PermSize；认为栈只会栈溢出不会 OOM；忽略逃逸分析与标量替换

### Q: 64G 堆的在线服务你选 G1 还是 ZGC，STW 停在哪几步？
- 领域: 语言
- 难度: 高级
- 考察点: 收集器实现与停顿构成，选型有没有量化依据
- 参考答案要点: G1 把堆切成 1~32MB 的 Region（目标约 2048 个），靠 Card Table + Remembered Set 解决跨 Region 扫描，-XX:MaxGCPauseMillis=200ms 只是停顿预测目标，Mixed GC 按回收价值挑 Region，JDK9 起为默认；STW 在 Initial Mark、Remark、Cleanup 三处；ZGC 用着色指针（借 3 个标记位）+ 读屏障做并发标记与转移，停顿 <1ms 且不随堆增大，JDK21 分代 ZGC 补短命对象回收，代价是吞吐略低、RSS 更高；Full GC 触发：Metaspace 不足、System.gc()、晋升失败、concurrent mode failure、Humongous 分配失败，Serial Old 在 64G 上能停几十秒
- 追问: 大量 Humongous Region 怎么处理？堆涨到 512G 你还选 ZGC 吗，为什么？
- 评分标尺: 及格=说出 G1 分区与 ZGC 低停顿；良好=讲清 STW 阶段与 Full GC 触发条件；优秀=能指出 RSet 内存开销与 ZGC 吞吐/RSS 代价
- 常见误区: 说 ZGC 完全没有 STW；把 MaxGCPauseMillis 当硬承诺；以为 Full GC 只在老年代满时发生

### Q: volatile 到底保证了什么，happens-before 怎么支撑双重检查锁？
- 领域: 语言
- 难度: 高级
- 考察点: JMM 抽象与内存屏障，而不是把 volatile 当原子开关
- 参考答案要点: happens-before 至少说得出程序顺序、监视器规则（unlock 先于同锁后续 lock）、volatile 写先于后续读、传递性、start/join；volatile = 可见性 + 禁止重排，写时插 StoreStore 与 StoreLoad 屏障（x86 表现为 lock 前缀指令），读时插 LoadLoad/LoadStore；不保证原子性，i++ 是读-改-写三步，要 AtomicInteger（CAS + volatile value）；DCL 不加 volatile 时 `new` 的分配内存→执行构造→引用赋值可能被重排，别的线程拿到未初始化完的半成品对象；final 冻结靠构造结束前的 StoreStore，但 this 逃逸会破坏
- 追问: 为什么 volatile 写在 ARM 上比 x86 贵？happens-before 和物理时间先后是什么关系？
- 评分标尺: 及格=可见性+禁重排且明确不原子；良好=说出 3 条 hb 并解释 DCL 重排后果；优秀=能讲屏障类型、平台差异与 final 边界
- 常见误区: 断言 volatile 让 i++ 安全；把 hb 当成时间顺序；觉得不加 volatile 只是效率问题

### Q: synchronized 方法从字节码到内核锁经历了什么，JDK6 之后怎么优化？
- 领域: 语言
- 难度: 高级
- 考察点: 锁升级机制与其代价，能否对应真实竞争场景
- 参考答案要点: 字节码是 monitorenter/monitorexit，锁状态存对象头 Mark Word；无锁→偏向锁（CAS 写入线程 ID，JEP 374 使 JDK15 默认关闭、18 移除）→轻量级锁（栈帧建 Displaced Mark Word 后 CAS，失败即自旋）→重量级锁（膨胀成 ObjectMonitor，含 EntryList/WaitSet，抢不到就 park 进内核用 futex 挂起）；升级不可逆，重偏向要等 safepoint 批量撤销；wait 释放锁而 sleep 不释放；高竞争宜换 ReentrantLock（tryLock 超时、公平模式、多 Condition）或 StampedLock 乐观读；锁的是引用指向的对象，String 常量池与 Integer -128~127 缓存会意外共锁
- 追问: 偏向锁为什么被默认关掉？线上大量 BLOCKED 线程怎么排查？自旋多久膨胀由谁决定？
- 评分标尺: 及格=说清三层状态与 ObjectMonitor；良好=能讲 Mark Word 存锁位与膨胀的内核切换代价；优秀=能解释偏向锁失效原因并对比 ReentrantLock
- 常见误区: 以为 synchronized 一直是重量级内核锁；认为锁能降级；把 wait 和 sleep 混为一谈

### Q: JDK8 的 HashMap 是什么结构，为什么容量必须是 2 的幂？
- 领域: 语言
- 难度: 中级
- 考察点: 关键设计决策与阈值数字的掌握
- 参考答案要点: 数组 + 链表 + 红黑树；链表长度到 8 且数组长度 ≥64（MIN_TREEIFY_CAPACITY）才树化，否则优先扩容，桶内降到 6 退回链表（8/6 留迟滞防抖）；依据是随机哈希下桶长近似泊松分布，P(≥8) 约千万分之六；负载因子 0.75，size 超过 capacity×0.75 就 resize 且容量翻倍；hash 用 `h ^ (h >>> 16)` 让高 16 位参与；容量为 2 的幂才能用 `(n-1) & hash` 代替取模，且扩容时元素只可能留在原位或原位 + oldCap（判据 `e.hash & oldCap` 是否为 0）；1.7 头插法并发扩容会成环打满 CPU，1.8 尾插但并发仍会丢数据
- 追问: 负载因子为什么不是 1？key 用可变对象会怎样？ConcurrentHashMap 靠什么保证并发安全？
- 评分标尺: 及格=答出三种结构与 0.75；良好=讲清 8/64/6 三阈值与 2 的幂的位运算收益；优秀=能说扩容移动规则与 CHM 的 CAS+synchronized 桶级锁
- 常见误区: 只背 8 变树漏掉长度 64 前提；把 CHM 说成分段锁（JDK8 已无 Segment）

### Q: 线程池七个参数分别干什么，任务提交后的完整流转路径是什么？
- 领域: 语言
- 难度: 中级
- 考察点: 参数间的顺序依赖与 Executors 工厂方法的禁令
- 参考答案要点: corePoolSize、maximumPoolSize、keepAliveTime+TimeUnit、workQueue、threadFactory、RejectedExecutionHandler；流转：线程数小于 core 先建核心线程→否则 offer 入队→队列满才扩到 max→仍满执行拒绝策略（先入队后扩非核心，与 Tomcat 先扩线程相反）；策略四种：AbortPolicy（默认抛 RejectedExecutionException）、CallerRunsPolicy（调用者线程跑，形成背压降速）、DiscardPolicy（静默丢）、DiscardOldestPolicy（丢队头再提交）；Executors 风险：Fixed/Single 用无界 LinkedBlockingQueue 堆到 OOM，Cached/Scheduled 的 max 为 Integer.MAX_VALUE 导致线程爆炸；定参：CPU 密集约 N+1，IO 密集按 N×(1+等待/计算) 起步再压测；submit 的异常被包在 Future 里会静默
- 追问: 想让队列满之前先扩满线程怎么改？线上怎么动态调参并观测？keepAliveTime 对核心线程生效吗？
- 评分标尺: 及格=背全七参数与四种策略；良好=讲清先入队后扩的顺序与 Executors 禁用理由；优秀=能给出 setCorePoolSize 顺序坑与活跃度/队列长度/拒绝次数指标
- 常见误区: 以为线程先扩满再入队；把 submit 当成会自动抛异常；认为 allowCoreThreadTimeOut 默认 true

### Q: ReentrantLock 靠 AQS 怎么排队唤醒，state 和 CAS 各负责什么？
- 领域: 语言
- 难度: 高级
- 考察点: 同步器框架的建模能力，能否用 AQS 解释 Semaphore
- 参考答案要点: AQS = `volatile int state` + CLH 变体双向队列（Node 的 waitStatus：SIGNAL/CANCELLED/CONDITION）+ tryAcquire/tryRelease 模板方法；CAS 改 state 失败则 addWaiter 入队，自旋判断前驱是否 head，不是就 LockSupport.park，前驱释放时 unpark；非公平在 tryAcquire 里先直接 CAS 抢一次不排队，吞吐高但可能饥饿，公平版先查 hasQueuedPredecessors；Condition 的 await 把节点移入条件队列并完全释放锁，signal 再搬回同步队列；Semaphore 用 state 记许可数、读写锁把一个 int 拆成高 16 位读低 16 位写；CAS 依赖 Unsafe 的 lock cmpxchg，ABA 用 AtomicStampedReference 版本戳，热点计数改用 LongAdder 的 Cell 分片
- 追问: 为什么用 park/unpark 而不是 wait/notify？读锁能升级成写锁吗？无锁栈里 ABA 什么时候真出问题？
- 评分标尺: 及格=说清 state+队列+park；良好=能定位公平/非公平代码点并解释 Condition 转移；优秀=讲出读写锁位分割与 CAS 的单变量局限
- 常见误区: 认为非公平一定更好；说读锁可升级写锁；把 lock 的 Condition 与 synchronized 的 wait 混用

## Python 语言机制

### Q: Python 有 GIL 的话多线程还有意义吗，CPU 密集怎么并发？
- 领域: 语言
- 难度: 中级
- 考察点: GIL 成因的理解与按 IO/CPU 属性选并发模型
- 参考答案要点: GIL 是 CPython 解释器级互斥锁，保护引用计数等非原子内存管理，同一时刻只有一个线程执行纯 Python 字节码；IO 系统调用与 NumPy/zlib 这类 C 扩展会主动释放 GIL，所以多线程对 IO 密集有效；CPU 密集多线程不加速，还因切换与 GIL 争抢变慢，切换间隔由 sys.setswitchinterval()（默认 5ms）控制；CPU 正解是 multiprocessing/ProcessPoolExecutor（fork 有写时复制、spawn 安全但启动慢，数据靠 pickle 走 IPC，内存近乎翻倍）；常见混合模式是进程池 × 每进程一个 asyncio loop；3.13 起有实验性 no-GIL（PEP 703）构建但非生产默认
- 追问: 什么时候多进程反而不如 asyncio？一段纯 Python 的像素处理你会怎么加速？
- 评分标尺: 及格=说清 IO 释放 GIL、CPU 走多进程；良好=能给 switchinterval、fork/spawn 差异与混合模型；优秀=讲出 C 扩展释放 GIL 细节与 no-GIL 现状
- 常见误区: 断言 Python 多线程完全没用；把 GIL 当语言规范；把协程与多线程当同一种并发单位

### Q: asyncio 里一个 await 做了什么，为什么我写了 async 还是串行？
- 领域: 语言
- 难度: 高级
- 考察点: 协程调度单位与挂起点，能否识别伪并发与阻塞事件循环
- 参考答案要点: 事件循环单线程，靠 epoll/kqueue/IOCP 监听 fd，协程只在 await 处让出控制权、没有抢占；`await a(); await b()` 是真串行，要 asyncio.gather(a(), b()) 或 create_task 才并发（3.11+ 用 TaskGroup 做结构化并发，异常会取消兄弟任务）；time.sleep、requests、同步 DB 驱动、纯 CPU 循环都会卡死整个 loop，须改 asyncio.sleep、aiohttp、asyncio.to_thread/run_in_executor（默认线程池上限 min(32, cpu+4)）；超时用 wait_for 或 3.11 的 asyncio.timeout，gather 需 return_exceptions=True 才不被首个异常打断；协程对象不接住 create_task 返回值可能被 GC
- 追问: 一个 CPU 密集协程把 loop 卡住你怎么发现和补救？单进程 asyncio 能榨干几个核？
- 评分标尺: 及格=说清 await 让出与 gather 才并发；良好=能识别阻塞点并给 to_thread/进程池补救与超时语义；优秀=区分协程对象与 Task 并讲跨 loop 共享的坑
- 常见误区: 以为加 async 就自动并发；在协程里用 threading.Lock 或同步驱动；把 time.sleep 当异步写法

### Q: 生成器和迭代器有什么区别，为什么读大文件要用 yield？
- 领域: 语言
- 难度: 中级
- 考察点: 迭代协议与惰性求值的实际收益
- 参考答案要点: 可迭代对象实现 __iter__() 返回迭代器，迭代器实现 __next__()，耗尽抛 StopIteration，for 靠捕获它结束（手写 while True + next 忘了处理会吞异常）；函数体含 yield 即编译为生成器，调用时不执行任何代码，每次 next 恢复挂起帧（局部变量与执行位置都保留）；收益是内存 O(1) 而非 O(n)，10GB 日志可逐行 yield，且 islice 取前 n 条后下游根本不再计算；生成器是一次性的，二次遍历为空，这是把返回值从 list 改成 generator 最常见的故障；send/throw/close 让 yield 有返回值（协程前身），yield from 委托子生成器并透传 send、异常与 return；未消费的生成器关闭时才执行 finally
- 追问: 无限生成器怎么配合 zip 截断？生成器链中间抛异常外层怎么处理？
- 评分标尺: 及格=说清协议与省内存；良好=能指出一次性消费与 send/yield from 语义；优秀=能讲 finally 触发时机与生成器流水线设计
- 常见误区: 以为调用生成器函数就立刻执行；认为生成器可重复遍历；把推导式方括号与小括号的差异当风格

### Q: 装饰器的本质是什么，加上之后哪些元信息容易丢？
- 领域: 语言
- 难度: 中级
- 考察点: 语法糖展开方式与 functools.wraps 的实际影响
- 参考答案要点: `@deco` 等价 `f = deco(f)`，在模块导入时执行一次而非调用时，本质是运行时替换函数对象；无参装饰器两层闭包，带参数（@retry(times=3)）要三层：外层收参数、中层收函数、内层 wrapper；不加 functools.wraps 会丢 __name__/__qualname__/__doc__/__module__/__wrapped__，按名字注册的框架（FastAPI 路由、pytest、Celery）就失效；多个装饰器自下而上应用、自上而下执行，先鉴权还是先缓存有语义差别；lru_cache(maxsize=128, typed=False) 只接受可哈希参数，装饰实例方法会长期持有 self 造成泄漏且跨实例共享缓存；async def 必须写 await 感知的 wrapper
- 追问: 怎么让装饰器同时支持 @deco 和 @deco()？计时装饰器会不会影响 gather 的并发度？
- 评分标尺: 及格=答出等价形式与 wraps 丢元信息；良好=能讲三层结构、应用顺序与 async 正确写法；优秀=能指出 lru_cache 的方法泄漏与双模式兼容写法
- 常见误区: 忘加 wraps 只说函数名变了；以为装饰器每次调用才执行；用 lru_cache 装饰接收 list 的方法

## Go 语言机制

### Q: Go 的 goroutine 怎么被调度，G、M、P 各负责什么？
- 领域: 操作系统
- 难度: 高级
- 考察点: M:N 调度模型，能否区分 IO 阻塞与 syscall 阻塞
- 参考答案要点: G 是协程（初始栈约 2KB，连续栈按 2 倍增长并拷贝，上限默认 1GB），只是带 PC/SP 的结构体；M 是 OS 线程（runtime 上限默认 10000，超出直接 fatal）；P 是逻辑处理器，数量 = GOMAXPROCS（默认等于核数），持有本地队列 LRQ（容量 256）与 mcache，M 必须绑 P 才能跑 G；syscall 阻塞时 M 与 P 解绑（hand off），P 从空闲池取一个继续跑；网络 IO 不占 M，netpoller 用 epoll/kqueue/IOCP 把 G 挂到 fd，就绪后重新入队，这是百万协程能挂而不烧线程的原因；本地队列空先查全局队列再随机窃取其他 P 的一半；纯 CPU 长循环由 sysmon 检测超 10ms 后基于信号异步抢占（1.14 起）
- 追问: 死循环的 goroutine 会饿死别人吗？GOMAXPROCS 设成核数两倍会怎样？
- 评分标尺: 及格=说清 G/M/P 与本地队列；良好=区分 syscall 与 netpoll 并讲 hand off、work stealing；优秀=补上异步抢占版本演进与 GC assist
- 常见误区: 认为 goroutine 与线程一对一；把 channel 阻塞当 syscall；以为 1.14 前完全没抢占

### Q: channel 和 select 的规则是什么，向已关闭 channel 读写会怎样？
- 领域: 语言
- 难度: 中级
- 考察点: 并发语义边界与 panic 场景的记忆
- 参考答案要点: hchan = 环形缓冲 buf + sendq/recvq 等待队列 + 互斥锁；无缓冲是同步会合（收发须同时就绪），有缓冲发送方可继续；读已关闭 channel 返回零值且 ok=false，所以 `for v := range ch` 能自动退出；向已关闭 channel 发送 panic，重复 close 或 close nil channel 也 panic；nil channel 读写永久阻塞，可在 select 里用来动态禁用分支；多分支同时就绪时 select 伪随机选一个以防饥饿；超时用 time.NewTimer + Reset（循环里反复 time.After 会堆积定时器），取消走 context.WithTimeout 的 Done；close 只由发送方做，多发送方要用 WaitGroup 收敛后再关；recover 只在 defer 的函数里直接调用有效
- 追问: worker pool 里怎么保证任务全完成再关 channel？select 不加 default 会怎样？
- 评分标尺: 及格=说清关闭语义与 select 随机；良好=讲 nil channel、time.After 堆积与 close 归属；优秀=给出 WaitGroup+channel 收尾顺序与 channel vs Mutex 选型
- 常见误区: 以为读关闭 channel 会 panic；循环里用 time.After 不 Reset；多个 goroutine 各自 close

### Q: Go 里 slice 和 map 最容易埋的坑是什么，各举一例？
- 领域: 语言
- 难度: 中级
- 考察点: 引用类型底层结构，能否解释"改不动"与 fatal error
- 参考答案要点: slice 是 24 字节的头（指针+len+cap），传值只拷头：改元素影响调用方，但超 cap 的 append 重分配底层数组，调用方看不到，必须返回新 slice；`s[low:high]` 与原 slice 共享数组，对它 append 会覆盖原数据，要用三索引 `s[low:high:high]` 限容；`var s []int` 是 nil slice，len 为 0 且能 append，但 JSON 序列化成 null，与 `[]int{}` 不同；map 是指向 hmap 的指针，拷贝变量仍共享底层，语言有意不提供深拷贝；并发读写 map 抛 concurrent map read and map write 是 fatal error，recover 兜不住进程直接挂，需 RWMutex 或 sync.Map（读多写少、键集稳定才划算）；迭代顺序随机化不可依赖；删 key 不归还桶内存，要 clear(m)（1.21）或重建，且应 make(map, n) 预分配
- 追问: 函数里 append 筛选结果外面为什么没变？sync.Map 为何不适合高频写？
- 评分标尺: 及格=知道 append 重分配与 map 并发 fatal；良好=讲三索引限容、nil 与空 slice 序列化差异与两种并发方案选型；优秀=能补删 key 不缩容与迭代随机化
- 常见误区: 以为传 slice 是深拷贝；用 recover 兜并发 map 崩溃；依赖 map 遍历顺序

## 工程实践与协作

### Q: rebase 和 merge 的区别是什么，什么时候绝对不能 rebase？
- 领域: 项目
- 难度: 中级
- 考察点: 提交不可变性，以及改写共享历史的后果
- 参考答案要点: merge 生成有两个父的 merge commit，保留真实分叉拓扑、可追溯但图乱；rebase 把提交逐个重放成新 hash（commit 内容含 parent，等于全新提交），得到线性历史，利于 git bisect 与 review；铁律：只 rebase 本地或未推送分支，已共享的 main/develop 不能 rebase，否则协作者历史分叉；必须改写远端时用 `git push --force-with-lease`（远端被动过就拒绝）而非裸 -f；常用组合：`git pull --rebase` 免生 Merge branch 提交、`git rebase -i` 做 squash/fixup/reword、`--amend` 修最后一次、cherry-pick 移植到 release 分支；冲突成本不同：merge 一次解完，rebase 每个提交都要解，可用 rerere 复用解法；平台 Squash Merge 是折中，代价是丢细粒度提交与精确 blame
- 追问: 已合进 main 的分支还能 rebase 吗？squash 之后想找回单个提交怎么办？
- 评分标尺: 及格=说清线性与保留拓扑；良好=给出共享分支禁 rebase 的理由与 --force-with-lease；优秀=能讲 rerere、bisect 与 squash 的 blame 损失
- 常见误区: 习惯 push -f 覆盖远端；认为 rebase 更新就一定更好；不知道 hash 变化会坑到别人

### Q: 你做 code review 时主要看什么，怎么避免变成风格口水战？
- 领域: 项目
- 难度: 中级
- 考察点: 评审有没有优先级框架，能否盯风险而非表面
- 参考答案要点: 优先级：正确性（边界值、空/零/单元素、竞态、是否吞异常、重试是否幂等）> 影响面（迁移能否回滚、有无灰度开关、接口向后兼容）> 设计（抽象层次错位、重复造轮子）> 命名可读性 > 风格；风格交给 gofmt、ruff/black、ESLint、Checkstyle 与 CI 门禁；规模：单次审查超过约 400 行后缺陷发现率显著下降，要求小 PR 并把纯重构与行为变更拆成两个 PR；评论分级标注 blocking/nit/question，避免 nit 淹没风险；重点追问测试是否覆盖失败路径、断言是否有意义；同时看可观测性与安全：trace id 与日志级别、关键 metric、敏感信息是否落日志、越权是否校验资源属主、有无注入与硬编码密钥
- 追问: 作者坚持不改你怎么处理？老代码没测试又想重构，评审怎么保证安全？
- 评分标尺: 及格=能列命名/逻辑/测试三类；良好=给出优先级分层、400 行量级与工具分工；优秀=能讲 blocking/nit 分类、重构与行为分离及逃逸缺陷率度量
- 常见误区: 只挑格式拼写；把个人偏好标成 blocking；只看新增不看删除而漏掉回滚风险

### Q: 单元测试和集成测试的边界怎么划，mock 用多了有什么代价？
- 领域: 项目
- 难度: 高级
- 考察点: 测试金字塔的真实理解与 mock 的长期成本
- 参考答案要点: 边界按被测单元对外可观察的行为划，不按函数粒度：单测在同进程内、不触网不落盘、不依赖真实时钟与随机（Clock 或 time.Now 作为端口注入）；集成测试验证装配与真实协议（SQL 方言、序列化、事务传播），接缝在我们代码与别人实现之间；比例参考金字塔 70/20/10（单测/集成/e2e），倒三角是耦合过重的信号；mock 代价：断言绑定实现细节（校验调了 selectById(3)）导致重构时测试全红、mock 行为只是作者假设会与真实依赖契约漂移（真实返回 null 而 mock 返回空集合）、覆盖率虚高却没断到真实行为；对策：断言结果而非调用序列、用可内存化的真实实现（SQLite/H2/in-memory repo、Testcontainers 起真 MySQL/Kafka）、跨服务用 Pact 契约测试、增量覆盖率门禁设 80%
- 追问: 私有方法很难测，你怎么判断是测试问题还是设计问题？flaky 测试怎么治理？
- 评分标尺: 及格=能按依赖边界分两类测试；良好=讲出契约漂移与对策；优秀=能提出"难测即设计信号"、quarantine 与 property-based testing
- 常见误区: 声称 100% 覆盖却几乎无断言；给 getter 写测试；用 mock 复制真实依赖行为等于自测自

### Q: 你们项目的 CI 流水线分几个阶段，PR 门禁怎么做到又快又稳？
- 领域: 项目
- 难度: 中级
- 考察点: 阶段依赖与门禁设计，而不是只会跑一下测试
- 参考答案要点: 阶段：装依赖（缓存 lockfile/Go module/.m2）→ 格式化与 lint（秒级 fail-fast）→ 编译/类型检查 → 单测（matrix 分片并行并输出 coverage）→ 构建制品（Docker 多阶段分离 builder 与 runtime、层缓存与 BuildKit cache mount、打带 commit sha 的 tag 与 SBOM）→ 静态与依赖扫描（SAST、Trivy CVE）→ 覆盖率门禁 → 集成测试（Testcontainers）→ 部署 staging → 冒烟/e2e + 金丝雀看错误率与 P99 → 确认晋升 prod；提速：PR 门禁目标小于 10 分钟，靠受影响模块选择、分片、依赖与镜像层缓存、cancel-in-progress 取消旧提交；稳定性靠 needs/DAG 并行、flaky 治理（同用例连续失败两次就隔离，禁止无脑 retry）、保留测试报告与 artifact 并回写 PR 评论；secrets 用 OIDC 短期角色
- 追问: 集成测试太慢拖垮门禁你怎么排优先级？怎么防"CI 绿了线上却炸"？
- 评分标尺: 及格=列出 lint/测试/构建/部署；良好=给时长目标、DAG 并行与覆盖率门禁手段；优秀=能讲 flaky 隔离、增量测试选择与制品可追溯
- 常见误区: 所有测试塞一个阶段串行跑；把 CI 通过当可发布；用无限 retry 掩盖不稳定用例

### Q: 线上服务变慢，你怎么定位热点在哪段代码或哪个依赖？
- 领域: 系统设计
- 难度: 高级
- 考察点: 从外到内分层量化的排查路径，而非凭感觉优化
- 参考答案要点: 先定基线与范围：P99 还是吞吐劣化、单机还是全量、有无发布或流量变化；系统层用 top -H、pidstat -t 分清 CPU 忙还是 iowait；进程内采样：JVM 用 async-profiler 火焰图（-e cpu 与 -e wall 的区别，wall 才看得到阻塞等待，可避 safepoint bias）或 JFR，Go 用 net/http/pprof + go tool pprof（CPU 采 30s，另看 alloc/block/mutex，block 需 SetBlockProfileRate 开启），Python 用 py-spy top 无侵入采样；依赖层用 pg_stat_statements 或 performance_schema 抓慢查询与全表扫描，N+1 最普遍，再看连接池等待（HikariCP maximumPoolSize 默认 10、connectionTimeout 30s）；链路层用 OpenTelemetry 的 trace 按最长子 span 定位；典型归因：锁竞争（jstack 同一栈大量 BLOCKED）、GC 频繁、正则灾难性回溯、循环内 RPC、缓存击穿；改完必须在同一负载模型下用 wrk/JMeter 复测并留前后火焰图
- 追问: CPU 100% 但火焰图里没有业务方法，可能是什么？只有 P99 劣化而均值正常你从哪查？
- 评分标尺: 及格=会用 profiler 与慢查询排查；良好=按系统→进程→依赖→链路分层收敛；优秀=能识别 wall/cpu 差异、锁与 GC 等非计算热点并强调复测对照
- 常见误区: 一上来加日志调线程数；把常驻埋点当无成本；只看 CPU 忽略 iowait、池等待与 GC 停顿
