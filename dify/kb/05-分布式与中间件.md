## 分布式基础与一致性协议
### Q: CAP 和 BASE 分别讲什么？分区发生了系统该怎么选？
- 领域: 分布式
- 难度: 中级
- 考察点: 是否理解只有 P 发生时才被迫二选一，且取舍按数据项而非按系统整体
- 参考答案要点: P 无法避免，发生时 C 与 A 二选一，且按每类数据取舍：余额扣减选 CP、商品详情选 AP；BASE=Basically Available（分区期允许降级返缓存或排队写）+Soft state（副本允许短暂不一致）+Eventual consistency（有限时间内重试/对账收敛）；CP 代表 ZooKeeper/etcd（少数派存活即拒写），AP 代表 Cassandra（R+W>N 得强读）；BASE 是把强一致移出同步路径、用对账兜底，"最终"没有时间上界
- 追问: 既然最终一致能收敛，为什么账本还要上 Raft 强一致？；R+W>N 为什么能保证读到最新写，举例说明
- 评分标尺: 及格=答出 P 发生才谈取舍；良好=能按数据项区分并举真实系统；优秀=能指出无分区时 C/A 可兼得、BASE 必须配对账监控
- 常见误区: 说成 CAP 三选二整体选边；把 BASE 理解成不要一致性
### Q: 都说强一致性代价高，具体高在哪？能给点数字吗？
- 领域: 分布式
- 难度: 高级
- 考察点: 能否把代价量化到延迟、吞吐、可用性三个维度
- 参考答案要点: 写要多数派确认，延迟从单机亚毫秒变成至少一个 RTT（同机房 0.5–2ms，跨城 30ms RTT 下 etcd 写入掉到数千 TPS）；吞吐受 leader 串行化日志限制，3 副本需 2 ack、写放大≥1.5x；ZK/etcd 3 副本挂 2 个整体拒写，可用性主动让位；线性一致读要 ReadIndex/lease 再确认多数派，读不再免费；网络抖动还放大选举震荡
- 追问: 为什么 Raft 只允许 leader 写，follower 读为什么会读到旧值？；lease read 靠什么保证安全，时钟漂移多大就破
- 评分标尺: 及格=说出多数派慢、leader 瓶颈；良好=给 RTT/TPS/写放大量级；优秀=区分写读可用性三类代价并给缓解手段
- 常见误区: 只说慢不讲哪一步慢；认为线性一致读和本地读一样免费
## 共识算法
### Q: 讲讲 Raft 的选举和日志复制，为什么都强调多数派？
- 领域: 分布式
- 难度: 高级
- 考察点: 是否理解 term 加多数派交集如何保证一 term 一 leader、已提交日志不丢
- 参考答案要点: election timeout 随机 150–300ms 防选票瓜分，candidate 自增 term 广播 RequestVote，>N/2 票当选；日志写 leader 后 AppendEntries 带 prevLogIndex/prevLogTerm 做一致性检查并截断冲突，多数派落盘后 commitIndex 前移 apply；选举与写两个多数派必相交，新 leader 必含全部已提交条目；安全规则：只投给日志不早于自己的候选人（选举限制）、只直接提交当前 term 条目、旧条目被间接提交；心跳典型 100ms
- 追问: 选举超时要不要随机，都固定 300ms 会怎样？；旧 term 条目已复制到多数派为什么不能直接提交？；3 节点怎么无损扩到 5 节点
- 评分标尺: 及格=讲清两个 RPC 和多数派；良好=能解释 term 逻辑时钟与交集论证；优秀=能讲选举限制与间接提交并给反例
- 常见误区: 以为谁活得久谁当 leader；把心跳当可选机制
### Q: Paxos 和 Raft 到底什么区别？为什么工程上 Raft 赢了？
- 领域: 分布式
- 难度: 高级
- 考察点: 是否理解两者解同一共识问题，差异在日志约束与可实现性
- 参考答案要点: Basic Paxos 单实例对一个值共识：prepare 用提案号占位+accept 写值；做日志要 Multi-Paxos 复用 leader 跳过 prepare，日志允许空洞需补洞；Raft 分解为选举+复制+安全，强约束日志连续无空洞按序 apply，易推理可验证；稳定 leader 下性能相当（都一跳多数派写），Multi-Paxos 省心跳、Raft 靠心跳维持权威；Raft 赢在论文伪码可验证且有 etcd/TiKV 生产实现，代价是强主模型跨地域写转发不灵活
- 追问: acceptor 已接受 3 号提案，2 号的 accept 还能成功吗，为什么？；Multi-Paxos 比 Basic 要额外处理哪些工程细节
- 评分标尺: 及格=知道 Raft 易实现；良好=能讲无空洞 vs 允许空洞、单值 vs 日志框架；优秀=能对比心跳/跨地域并指出选型真实驱动
- 常见误区: 说 Raft 一致性强于 Paxos；认为 Paxos 不需要选主
## 分布式锁
### Q: 分布式锁你会怎么实现？RedLock 的争议到底在争什么？
- 领域: 分布式
- 难度: 高级
- 考察点: 是否理解锁的根因困难是持有者暂停加锁过期，以及何时该换原语
- 参考答案要点: Redis：SET key owner NX PX 30000，解锁必须 Lua 比对 owner 再 DEL，Redisson watchdog 每 10s 续约、TTL 30s；争议：Kleppmann 指出 RedLock（5 个独立 master 依次加锁取多数派、未超总 TTL 算成功）挡不住持有者 GC 暂停超 TTL 后继续写，根本解法是存储校验单调递增 fencing token；antirez 反驳称暂停不现实；结论：效率场景（防重复计算）可用 Redis 锁，正确性场景用 etcd lease+revision、ZK 临时顺序节点或 DB 唯一约束
- 追问: 解锁为什么不能直接 DEL？GC 暂停超过 TTL 会发生什么？；fencing token 在存储层具体怎么校验
- 评分标尺: 及格=会 SETNX+owner+Lua；良好=讲清暂停场景与 fencing 为何是根本解；优秀=按效率/正确性分类选型并给 ZK/etcd 性能代价
- 常见误区: 认为 RedLock 修好了正确性；指望调大 TTL 解决一切
## 缓存专题
### Q: 缓存穿透、击穿、雪崩分别是什么、怎么各防？
- 领域: 分布式
- 难度: 中级
- 考察点: 三者触发条件是否分得清，防御能否对应到机制
- 参考答案要点: 穿透=DB 根本没有该数据（恶意 id=-1）缓存永远 miss：缓存空值 TTL≤60s、布隆过滤器前置拦截、入口校验限流；击穿=单个热 key 过期瞬间被并发重建打穿：setnx 互斥只放一个请求查库回填，或 value 带逻辑过期字段先返旧值异步刷新；雪崩=大批 key 同时过期或 Redis 整体宕：TTL 加 0–300s 随机抖动、Caffeine+Redis 两级、DB 前熔断限流、Redis 哨兵/cluster 保可用
- 追问: 缓存空值会不会被恶意 key 撑爆内存，怎么配？；互斥重建时没抢到锁的请求是等待还是返旧值？；Redis 重启后全量 miss 算哪一种
- 评分标尺: 及格=三定义不混且各有方案；良好=能讲互斥与逻辑过期取舍；优秀=区分防 miss 与防 DB 打死两层并有限流兜底
- 常见误区: 击穿穿透说反；认为布隆过滤器能防击穿
### Q: 缓存和数据库双写怎么保证一致？延迟双删和订阅 binlog 各解决什么？
- 领域: 分布式
- 难度: 高级
- 考察点: 能否画出双写竞态时序，说清两种补丁各堵哪个洞
- 参考答案要点: 危险时序（先删后改）：A 删缓存→B miss 读旧值→B 回填→A 更新 DB，缓存永久旧；推荐先更新 DB 再删缓存，加延迟双删：删→更新→sleep 500ms–1s（覆盖一次读+回填与主从延迟）→再删，二次删除走 MQ；Canal 订阅 binlog（伪装 slave、row 格式）：业务只写 DB、异步消费变更删/回填缓存，解耦且按位点可重放，代价多一跳百 ms；两者都是最终一致，用版本对账（Redis 存 updated_at）兜底，秒级都不能忍的场景不该用缓存
- 追问: 500ms 依据什么定，主从延迟 2s 时还成立吗？；第二次写插进两次删除之间，缓存最终是旧是新？；Canal 消费者删完缓存就宕机怎么办
- 评分标尺: 及格=能画竞态并说出删缓存不写缓存；良好=讲清延迟双删参数与 Canal 架构；优秀=明确只是把窗口缩到百 ms、要对账兜底
- 常见误区: 说加分布式锁就行；把延迟双删当银弹不看主从延迟
### Q: 一个 key 每秒被读几十万次，Redis 单分片顶不住，热 key 怎么发现和治理？
- 领域: 分布式
- 难度: 高级
- 考察点: 热点定位手段与分层治理，理解打散读与原子性的矛盾
- 参考答案要点: 发现：--hotkeys（需 LFU 策略）、proxy/客户端埋点统计 key 级 QPS、云厂商热 key 探测（采样+滑动窗口）；危害：单分片单线程约 8–10 万 QPS 封顶，一个 key 打满一片而集群空闲；治理：本地 Caffeine 1–5s 短 TTL 扛读（库存类禁用）、拆 key 为 hotkey_0..99 读随机挑、该分片挂 slave 读写分离、写热计数器本地聚合 HINCRBY 定时刷、热点自动发现框架 client 上报 worker 判定推送网关
- 追问: 本地缓存 1–5s 陈旧按什么标准判断可否接受？；拆片破坏原子性，要 CAS 的余额怎么办？；网卡 1Gbps、value 10KB 算单 slave 读上限
- 评分标尺: 及格=会发现+本地缓存；良好=拆 key/读写分离/写聚合全齐；优秀=能给自动发现架构并量化分片上限
- 常见误区: 以为 LRU 下也能跑 --hotkeys；用加节点解决单 key 热点
## 消息队列
### Q: 用 MQ 之后，不丢、不重、有序这三件事分别怎么做？
- 领域: 分布式
- 难度: 高级
- 考察点: 能否按生产端-Broker-消费端三段拆可靠性，讲清有序与吞吐的矛盾
- 参考答案要点: 不丢：生产端同步发送判 ack（Kafka acks=all+min.insync.replicas=2、RocketMQ 同步双写、RabbitMQ confirm）、Broker 多副本 ISR 收缩告警、消费端关 auto.commit 业务成功再手动 ack；不重=至少一次必然可能重复，靠消费幂等：唯一键+DB 唯一索引、msg_id 去重表、状态机 CAS；有序：全局有序=单 partition 单 consumer 吞吐崩塌没人用，局部有序按业务 key 路由（Kafka 同 key 同分区、RocketMQ 按 orderId 选队列）+单线程消费，失败重试会乱序只能本地阻塞重试或挂起队列
- 追问: acks=all 到底要谁确认，和 min.insync.replicas 怎么配合？；顺序消费一条重试 3 次仍失败，后面的消息怎么办
- 评分标尺: 及格=三段防丢+幂等防重+按 key 保序；良好=ISR/双写参数级机制；优秀=点出至少一次+幂等是唯一出路并处理重试与有序冲突
- 常见误区: 以为 acks=all 就永不丢却忽略消费端提交；多线程消费还声称局部有序
### Q: 消息反复消费失败怎么办？死信队列是怎么设计的？
- 领域: 分布式
- 难度: 中级
- 考察点: 是否对失败分类、用退避控风险、让失败可观测可闭环
- 参考答案要点: 分类：可恢复（超时/5xx/死锁）进重试通道，不可恢复（反序列化失败/业务校验不过）直接进死信防重试风暴；RocketMQ 默认重试 16 次、间隔走 delayLevel 表 10s/30s/1m/2m…2h，耗尽投 %DLQ% 组；RabbitMQ 用 x-dead-letter-exchange+TTL 串多级重试队列；Kafka 无原生重试，header 记 retryCount 投 retry topic；死信处置：落库+告警（死信量是 SLA 指标）、限速幂等重投、保留 7–14 天
- 追问: 固定 10s 重试在下游刚恢复时有什么风险，为什么退避要加 jitter？；进死信算丢消息吗，闭环 SLA 怎么定
- 评分标尺: 及格=知重试+死信概念；良好=能按故障分流并说三家 MQ 实现差异；优秀=重投限速幂等与告警指标完整
- 常见误区: 所有异常无脑重试；死信当垃圾桶无人看管
## 流量治理
### Q: 令牌桶、漏桶、滑动窗口限流有什么区别？阈值这个数怎么定？
- 领域: 分布式
- 难度: 中级
- 考察点: 各算法对突发的态度，且阈值必须来自压测而非拍脑袋
- 参考答案要点: 固定窗口临界突发可达 2 倍限额，滑动窗口用 ZSET 时间戳或分桶（Sentinel 默认 1s 切 2 桶）减小误差；漏桶恒速率出水强平滑、不容任何突发，适合保护脆弱下游；令牌桶按速率 r 产 token、容量 b 决定突发上限，Guava SmoothBursty 默认 maxBurstSeconds=1s、冷启动用 Warmup；分布式用 Redis+Lua 原子补币取币或网关卡；阈值=单机压测 P99 仍达 SLA 的最大 QPS（如 800）×节点数×0.7–0.8 水位，再按下游容量封顶；多租户按 tenant+api 分配额桶防饿死
- 追问: 会来 100 倍微突发时 r 和 b 怎么配？；Redis+Lua 在 10 万 QPS 下瓶颈在哪，和本地桶+配额下发怎么权衡？；拒绝和排队各适合什么语义
- 评分标尺: 及格=区分漏桶平滑/令牌桶容突发；良好=给分布式实现与窗口误差分析；优秀=阈值出自压测并讲配额分配
- 常见误区: 说令牌桶不允许突发；拍 QPS 当阈值不看下游容量
### Q: 熔断、降级、隔离是三个概念吗？熔断阈值和状态机怎么设计？
- 领域: 分布式
- 难度: 中级
- 考察点: 三者保护目标各异，熔断参数要与真实故障形态匹配
- 参考答案要点: 隔离=结构防传染：线程池/信号量分舱（Hystrix 默认共享 Tomcat 线程+每依赖信号量）、连接池分舱；熔断=状态机 closed→错误率或慢调用比例超限转 open 快速失败→waitDuration（Resilience4j 默认 60s）后 half-open 放行少量探测→成功回 closed；Sentinel RT 模式=最大 RT 500ms+慢调用比例 0.8+最小请求数 5；降级=功能取舍：返缓存/默认值、砍推荐保下单；配套每依赖 timeout<上游剩余 deadline、重试带 jitter 且受熔断约束
- 追问: 下游 P99 恶化到 800ms 但错误率 0%，只看错误率的熔断为什么不救？；half-open 放几个探测请求，为什么不能全放开？；核心接口优先降级还是限流
- 评分标尺: 及格=三者定义不混；良好=能画状态机并给参数；优秀=指出 RT+错误率双信号、按依赖粒度熔断并配超时预算
- 常见误区: 把降级当熔断同义词；忘了重试风暴让熔断一直 open
### Q: 幂等要在哪些环节做？机制层面具体怎么实现？
- 领域: 分布式
- 难度: 中级
- 考察点: 是否知道硬保证只能落在存储唯一约束上，判重与写入必须原子
- 参考答案要点: 触发源：超时重试、MQ 重投、支付回调重复通知、重复提交；硬保证=DB 唯一索引（订单号+事件类型，撞 duplicate key 当成功）+状态机 CAS：UPDATE orders SET status='PAID' WHERE id=? AND status='UNPAID'，影响行数 0 即重复；Redis SETNX 幂等键存结果快照、TTL≥最大重试窗口（支付 24h）；令牌模式提交时 Lua 原子删 token；关键坑：SELECT 判重+INSERT 有并发洞，判重与业务写必须同一原子操作；幂等键全链路透传（网关→服务→MQ）
- 追问: SETNX 成功但业务执行中 crash，算处理过吗，怎么恢复语义？；为什么支付回调幂等键用渠道交易号而不是订单号
- 评分标尺: 及格=唯一索引+状态机两板斧；良好=键与 TTL 设计有依据、讲透原子性；优秀=能处理部分成功的补偿与对账
- 常见误区: 用先查后插当原子判重；Redis 去重了就不管 DB 唯一键
## 全局 ID 与事务
### Q: 雪花算法 ID 怎么生成的？机器时钟回拨了怎么办？
- 领域: 分布式
- 难度: 中级
- 考察点: 位段数字是否准确，回拨处理有没有分层思路
- 参考答案要点: 64bit=1 符号+41 毫秒时间戳（自定义 epoch 约可用 69 年）+10 workerId（5 数据中心+5 机器共 1024 台）+12 序列号（同毫秒 4096 个，单机理论 409.6 万/秒）；趋势递增利于 InnoDB 主键（UUID 随机写页分裂）；回拨：几 ms 内自旋等追平（Seata 默认约 5ms 内等待、超过抛异常），大幅回拨该机下线换 workerId；规避方案=号段（美团 Leaf：UPDATE max_id=max_id+step 每次取 1000、双 buffer 用尽前预取，不依赖时钟，重启只跳号）；workerId 用 ZK 顺序节点/配置租约防撞
- 追问: 41 位时间戳为什么不从 1970 起算？；号段重启丢剩余号段，什么业务绝不能断号？；雪花会暴露业务量级吗
- 评分标尺: 及格=位段与吞吐正确；良好=回拨策略分档给阈值；优秀=能对比 UUID/号段并讲 workerId 分配细节
- 常见误区: 说雪花全局严格有序（跨机仅趋势递增）；以为加个等待就能解决回拨
### Q: 分布式事务怎么做？2PC、TCC、本地消息表、Saga 各有什么代价？
- 领域: 分布式
- 难度: 高级
- 考察点: 能否按一致性强度、耦合度、性能三个轴选型
- 参考答案要点: 2PC/XA：全员 prepare 后 commit，prepare 锁资源、协调者单点致悬挂，吞吐只有本地事务零头；TCC：Try 冻结/Confirm/Cancel，锁窗口缩到业务字段，但要解空回滚（Cancel 先到需事务控制表禁后续 Try）、悬挂（Try 后到要拒绝）、Confirm/Cancel 幂等；本地消息表：与业务同事务落表+异步投递+消费幂等，最终一致延迟秒级（RocketMQ 事务消息=半消息+本地事务+反向 check back 免建表）；Saga：本地事务序列+补偿动作，无冻结吞吐高但隔离弱、脏读要语义反转；选型：资金强同步 TCC、解耦高并发事务消息、长流程 Saga、XA 仅低并发内网
- 追问: TCC 的 Try 冻结超时多久释放，Confirm 一直失败怎么办？；事务消息为什么必须回查本地事务状态？；Saga 补偿本身失败怎么办
- 评分标尺: 及格=四种模式流程讲对；良好=TCC 三坑与 check back 细节；优秀=给选型矩阵并量化性能差距
- 常见误区: 把 TCC 当强一致默认答案；认为本地消息表能免除消费幂等
## 数据分片与高可用
### Q: 分库分表为什么用一致性哈希？虚拟节点是干嘛的？
- 领域: 分布式
- 难度: 中级
- 考察点: 能否推导扩缩容迁移量，区分分布均匀与访问均匀
- 参考答案要点: hash mod N 增删节点时槽位近乎全部重排、搬迁混乱；一致性哈希把 key 与节点映到 0..2^32-1 环、顺时针取最近节点，增删一个节点只动相邻段、期望迁移 1/N；虚拟节点解决物理点少时环上区间长度方差大（3 节点可倾斜 3–5 倍）：每物理节点插 150–1000 个虚拟点（ketama 默认 160）拉平分布；副本要放到相隔足够虚拟点距的不同物理机；对比 Redis Cluster 用固定 16384 槽+CRC16，因槽可显式 MIGRATING、运维可干预
- 追问: 一致性哈希新增一台机器约迁移多少流量，怎么推导？；虚拟节点解决不了什么问题（热点 key）？；Redis 为什么选槽不选一致性哈希
- 评分标尺: 及格=讲清环与顺时针归属；良好=给迁移率推导和虚拟点数量级；优秀=能对比槽方案指出运维差异
- 常见误区: 说一致性哈希解决热点；认为虚拟节点越多越好
### Q: 刚写完立刻读从库读到旧数据，原因和解决办法？
- 领域: 分布式
- 难度: 高级
- 考察点: 是否理解延迟出在复制哪一段，读己之写有几种实现
- 参考答案要点: 异步复制：主提交→dump 推 binlog→IO 线程写 relay log→SQL 线程回放，延迟主要在回放：5.6 前单线程、大事务/无主键 DDL 滞秒到分钟级，5.7+ slave_parallel_workers=4 按 logical clock 并行；解法：会话粘性写后读强制走主（ProxySQL/ShardingSphere）、GTID 等待（拿主库 gtid_executed 在从库执行 SELECT WAIT_FOR_EXECUTED_GTID_SET 再读）、关键会话数据写 Redis miss 回主、半同步 AFTER_SYNC 只保证不丢不保证已回放、或该表干脆不读写分离
- 追问: AFTER_SYNC 和 AFTER_COMMIT 区别，为什么说 AFTER_COMMIT 有幻读死亡？；Seconds_Behind_Master 有什么缺陷（IO 断开显示 0）？；读主流量大了怎么收窄窗口
- 评分标尺: 及格=知延迟原因与读主；良好=讲并行复制与 GTID 等待原理；优秀=能区分半同步语义边界并给监控细节
- 常见误区: 认为半同步解决读旧数据；只信 Seconds_Behind_Master
### Q: 分库分表后，全局唯一 ID、不带分片键的查询、跨分片排序分页怎么办？
- 领域: 分布式
- 难度: 高级
- 考察点: 分片后三大经典难题是否有代价可控的方案并能算数
- 参考答案要点: 全局唯一：应用层雪花/号段（多分片自增必撞号）；无 shardKey 查询=广播 32 片、P99 由最慢片定：基因法（用户 ID 哈希尾数编进订单号，按用户分片则订单号同路由）、映射表（手机号→用户 ID 两张分片表二跳）、ES 异构宽表（binlog 同步拿 ID 回表，接受秒级延迟）；分页：各片取 LIMIT offset+n 归并，第 100 页×千片=拉 10 万行，改游标 WHERE (create_time,id)<(cursor) LIMIT 20、产品只允许下一页；聚合：SUM/COUNT 中间件下推，复杂分析走 ClickHouse；原则：单表<5000 万行/100GB 不分片，先归档分区加缓存
- 追问: 基因位预留几位、不够用怎么办？；游标分页中途插入新数据为什么会漏/重？；要不要分片的阈值依据是什么
- 评分标尺: 及格=三问各有一方案；良好=基因/映射表/ES 细节与取舍；优秀=能算深翻页成本并质疑分片必要性
- 常见误区: 用 UUID 当全局方案（索引灾难）；忽略 ES 同步延迟；分片键选低基数字段
