# 知识库语料格式规范（面试陪练官 · seekdb 混合检索）

用途：这些 Markdown 文件会被导入 Dify 知识库（底层向量库 = 真实 seekdb，HNSW 向量索引 + ik 全文索引 + 混合检索）。
写作目标不是"百科全书"，而是**让检索命中后能直接支撑面试官出题、追问、评分**，所以每条都要自成一体（不依赖上下文也能读懂）。

## 分块约束（重要）

Dify 默认按 Markdown 标题 / 空行分段，检索以"段"为单位。因此：

- 一个 `###` 小节 = 一道题 = 一个检索块，**内部不要出现空行**（用列表项换行），避免被切碎。
- 每个小节控制在 **150–450 字**，太短召回信息不足，太长稀释向量。
- 文件用 `##` 分主题，`###` 列题目；文件开头不要写前言套话，直接 `## 主题名`。

## 每条题目的固定模板

```
### Q: <候选人会听到的原题，口语化，一句问完>
- 领域: <数据库/操作系统/网络/算法/分布式/语言/项目/行为面/系统设计>
- 难度: <初级|中级|高级>
- 考察点: <一句话，面试官真正想确认的能力>
- 参考答案要点: <3–6 条，用分号连接，必须具体到机制/参数/数字，禁止"看情况"这类空话>
- 追问: <2–3 个连环追问，每个都是完整问句，用分号连接>
- 评分标尺: <及格=答到X；良好=补上Y；优秀=能讲清Z 或指出前提与代价>
- 常见误区: <1–3 条候选人典型错误说法，用分号连接>
```

字段名必须严格照抄（`领域` `难度` `考察点` `参考答案要点` `追问` `评分标尺` `常见误区`），后续脚本按字段解析。

## 内容质量底线

1. 技术题必须写**机制层面**的答案，不写"多练习"这种废话。有具体名词就写具体名词（如 InnoDB undo 日志版本链、ReadView、`innodb_lock_wait_timeout`）。
2. 至少 30% 的题带**数字或参数**（默认值、复杂度、量级），这是"优秀"档的区分点。
3. `追问` 要能连成真实面试的一串对话，第二问基于第一问答案深入。
4. 全部中文；英文术语保留原词（如 MVCC、ReadView、TCP_NODELAY）。
5. 不要写免责声明、不要写"作为 AI"、不要在文件末尾加总结。
