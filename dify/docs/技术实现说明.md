# 技术实现说明

对应交付物：`dify/dsl/interview-coach.yml`（应用）、`dify/retrieval/`（自研混合检索工具）、`dify/embedding/`（本地向量化服务）、`dify/kb/`（语料）。

## 1. 整体结构

```
                       ┌──────────────────────── Dify 1.18.0（本地 docker compose）────────────────────────┐
 评委对话 ──▶ Web/Service API                              │                                                            │
                       │  Chatflow: seekdb 面试陪练官（advanced-chat）                                      │
                       │  start ─▶ code(模式路由) ─┬─▶ knowledge-retrieval ─┐                              │
                       │                           └─▶ tool(自定义工具)   ─┴─▶ code(检索小结) ─▶ llm ─▶ answer │
                       └──────────────────────────────┬───────────────────────────┬──────────────────────┘
                                                       │                          │  HTTP(经 ssrf_proxy)
                                        VECTOR_STORE=seekdb                       ▼
                                                       │                 宿主机 :3012  dify/retrieval/server.mjs
                                                       ▼                          │  mysql2(2881)  +  宿主机 :8100 embedding
                                          ┌──────────────────────┐                │
                                          │   seekdb 容器:2881    │◀───────────────┘
                                          │ 库 test               │
                                          │ vector_index_<dataset>_node
                                          │  · VECTOR(512) + VECTOR KEY vector_index (HNSW/VSAG/L2)
                                          │  · longtext text   + FULLTEXT KEY fulltext_index_for_col_text (ik smart)
                                          └──────────────────────┘
```

关键点：**知识库向量表和自研工具查的是同一张 seekdb 表**（表名 `vector_index_<dataset_id>_node`）。Dify 负责写入（切片 → 调本地 embedding → 落 seekdb），自研工具负责以可控模式再读一次，两条通路可以互相印证，也能在同一张表上直接对比检索方式差异。

## 2. 通路 A：seekdb 作为 Dify 原生向量库

Dify 1.18 的 OceanBase/seekdb 向量库实现在 `providers/vdb/vdb-oceanbase`（容器内路径 `/app/api/providers/vdb/vdb-oceanbase/src/dify_vdb_oceanbase/oceanbase_vector.py`）。开启方式全部是 compose 侧配置，无需改 Dify 代码：

| 配置项（`docker/envs/vectorstores/seekdb.env`） | 取值 | 作用 |
| --- | --- | --- |
| `VECTOR_STORE`（`.env`） | `seekdb` | 选中 seekdb 作为知识库向量库 |
| `OCEANBASE_VECTOR_HOST/PORT/USER/PASSWORD/DATABASE` | `seekdb` / `2881` / `root` / 占位口令 / `test` | 容器内连接串 |
| `OCEANBASE_ENABLE_HYBRID_SEARCH` | `true` | 允许混合检索；provider 会先 `_check_hybrid_search_support()` 校验版本（需 ≥ 4.3.5.1） |
| `OCEANBASE_FULLTEXT_PARSER` | `ik` | 全文索引分词器，中文必须显式指定，否则默认按空格切，中文检索基本不可用 |

建表结果（`evidence/seekdb-table-ddl.txt`，为 Dify 实际执行产生的 DDL）同时含三类索引：

```sql
VECTOR KEY `vector_index` (`vector`) WITH (LIB=VSAG,DISTANCE=L2,M=16,EF_CONSTRUCTION=256,TYPE=HNSW,EF_SEARCH=64),
FULLTEXT KEY `fulltext_index_for_col_text` (`text`) WITH PARSER ik PARSER_PROPERTIES=(ik_mode="smart"),
KEY `idx_metadata_doc_id` ((cast(JSON_UNQUOTE(JSON_EXTRACT(`metadata`,'$.document_id')) as char(64) charset utf8mb4))) LOCAL
```

`SHOW INDEX` 里 `VECTOR` 与 `FULLTEXT` 两个 Index_type 同时存在（`evidence/seekdb-native-proof.txt`），并且只用全文条件也能召回到正确题目（`MATCH(text) AGAINST('ReadView')` Top1 = MVCC 那道题，fts_score 7.431）。这里要留意一个条件：**混合索引是否建立取决于知识库自己的 `retrieval_model.search_method`**。只有该值为 `hybrid_search` 时，Dify 的检索节点才会同时发语义与全文两路（`core/rag/retrieval/retrieval_methods.py`：`HYBRID_SEARCH` 同时满足 `is_support_semantic_search` 与 `is_support_fulltext_search`），两路结果合并后按分数排序取 top_k。所以导入脚本之后必须执行 `scripts/set-dataset-hybrid.mjs` 把知识库切到 hybrid_search——这是很多人复现时踩的坑，切完不需要重建库。

知识检索节点在演示中的实测输出（`evidence/run-*.json` 的 `summary.知识库检索`）：每轮固定 5 条命中，Top1 score 落在 11.9-47.1 区间（Dify 的 hybrid 分数是全文分与向量分合并后的值，量纲不是 0-1 余弦，不能直接当相似度读），节点耗时 0.10-0.22s。以「InnoDB 的 MVCC 是怎么保证一致性读的？」为例（`run-two-turns.json` 第 1 轮），5 条命中里 4 条来自 `01-数据库原理与InnoDB`，Top1 是「ACID 四个特性…」（score 11.928），MVCC 那道题在前 3 位之外；第 2 轮候选人直接报出 ReadView 这个术语后，「讲讲 MVCC 的实现」跃到 Top1 且 score 47.141——术语命中时全文通道的分量明显压过语义相似度，这正是混合检索的行为特征。

## 3. 通路 B：自研 seekdb 混合检索工具

`dify/retrieval/server.mjs`（Node，无框架，监听 :3012）用 mysql2 直连 seekdb，把 Task3 里验证过的混合检索逻辑做成 Dify 可调用的一次 HTTP 请求：

```sql
SELECT * FROM (
  (SELECT id, text, metadata, MATCH(`text`) AGAINST(?) AS score, 1 AS in_fts, 0 AS in_vec
     FROM <table> WHERE MATCH(`text`) AGAINST(?) LIMIT 20)
  UNION ALL
  (SELECT id, text, metadata, l2_distance(vector, '<512维查询向量>') AS score, 0 AS in_fts, 1 AS in_vec
     FROM <table> ORDER BY score APPROXIMATE LIMIT 20)
) t
```

实现要点（都是踩过的坑，写在代码注释里）：

- OceanBase 里 `UNION ALL` 两侧分支必须各自加括号，否则 `ER_PARSE_ERROR`。
- 两个分支的打分列**必须同名**（这里统一叫 `score`）。UNION ALL 的结果列名取自第一个分支，若一个写 `fts_score` 一个写 `vec_score`，第二分支的分数会被塞进第一列而 `vec_score` 恒为 NULL，消融数据就会误报成"向量通道没打分"。
- 融合用应用层 RRF（K=60）：`rrf = Σ 1/(K + rank)`，同时保留每条素材在两路里的名次（`channels: "fts:1,vec:3"`）与原始分数（`fts_score` / `vec_distance`），这样"命中"可解释，不依赖黑盒分数。
- 三种模式：`hybrid`（两路都取）/ `vector`（只 bump 向量路）/ `fts`（只 bump 全文路）——同一份数据、同一张表，只切换检索方式，保证消融可比。
- `explain=true` 时附带 `EXPLAIN` 输出。seekdb/OceanBase 的执行计划是单个 `Query Plan` 文本列（树状），其中 `Outputs & filters` 段会把 512 维查询向量原样打出来（几百 KB），所以默认截断到算子树、并对超长行做掩码；`explain_detail=true` 可取全文。
- 查询向量来自 `dify/embedding`，与 Dify 写入时用的是同一个模型（`Xenova/bge-small-zh-v1.5`，512 维，q8 ONNX），避免"写向量"和"查向量"不同源导致的距离失真。

该服务以 OpenAPI 3.0 schema（`retrieval/openapi.yaml`，`operationId: seekdb_hybrid_search`）注册为 Dify 自定义工具：`scripts/setup-custom-tool.mjs` 走控制台 API `POST /workspaces/current/tool-provider/api/add`，凭据 `auth_type: none`，幂等（同名先删再加），`--test` 会真实调用一次 `POST /tool-provider/api/test/pre`。

**SSRF 代理这一关**：Dify 的自定义工具调用一律经 `ssrf_proxy`（squid），默认 `http_access deny to_private_networks`，容器访问宿主机 `host.docker.internal`（解析为 `192.168.65.254`）会被直接 `ERR_ACCESS_DENIED`。解决方式是 `.env` 里 `SSRF_PROXY_ALLOW_PRIVATE_IPS=192.168.65.254` 后重建 ssrf_proxy 容器（Dify 1.18 的 `docker-entrypoint.sh` 会据此生成 `dify_allow_private.conf`）。

## 4. Chatflow 节点设计

DSL 版本 `0.7.0`，模式 `advanced-chat`，7 节点（`dsl/interview-coach.yml`，服务器规范版见 `dsl/interview-coach.exported.yml`）：

| 节点 | 类型 | 作用 | 实测耗时 |
| ---- | ---- | ---- | -------- |
| 开始 | start | 收 `sys.query` | ~0s |
| 模式路由 | code(python3) | 只认**句首**的开关词识别 `vector`/`fts`/`hybrid`，剥掉开关得到干净 query；检测「证据/执行计划/explain」决定是否取 EXPLAIN；产出 `mode_label` | 0.05-0.08s |
| 知识库检索（seekdb 原生混合） | knowledge-retrieval | 通路 A，`dataset_ids` 指向本知识库，`query_variable_selector` 取 code 的 `clean_query`，top_k=5，不重排 | 0.10-0.22s |
| seekdb 混合检索工具（可消融） | tool | 通路 B，参数 `query/mode/explain` 由 code 输出注入，`top_k=4` 常量；开启 2 次重试 | 0.03-0.19s |
| 检索小结（确定性） | code(python3) | 把两条通道的真实命中数与 `took_ms / embed_ms` 排成固定一行；数字用字符串定位从工具返回的 JSON 里取，不让模型转述 | 0.06-0.08s |
| 面试官 | llm | `langgenius/deepseek/deepseek` + `deepseek-flash`，temperature 0.25，context 取知识检索节点的 `result`，记忆窗口 12 轮，`reasoning_format: separated` | 3.2-6.7s |
| 回答 | answer | `{{#1000000000005.text#}}` 之后固定追加 `{{#1000000000007.summary#}}` | ~0s |

提示词把"检索"和"教学"绑在一起，共 7 条工作规则 + 3 条输出格式约束，其中四条与 seekdb 直接相关：规则 1 只允许使用检索到的素材（素材没有就答"这块题库里没有，换个方向"，把幻觉变成可观测行为）；规则 5 双通道不一致时以知识库为主并说明差异来自哪条通道；规则 6 明确**禁止**模型自己写「检索小结」或转述命中数量、毫秒数（这些数字由「检索小结」代码节点从 seekdb 返回值里取，再由回答节点追加）；规则 7 把句首开关识别为控制指令，不许模型拿它当答案内容来点评。出现"证据"字样时，把 seekdb 的 EXPLAIN 算子树放进代码块并解释 `TEXT RETRIEVAL SCAN` ↔ `fulltext_index_for_col_text`、`VECTOR INDEX SCAN` ↔ `vector_index`。

为什么开关只认句首：早先写成 `"向量" in query`，于是「向量数据库怎么选型」被判成纯向量、「全文索引和倒排的关系」被判成纯全文，消融对照当场失真。现在强关键词（`纯向量 / 只走向量 / 仅向量 / 纯全文 / 只走全文 / 仅全文 / 关键词`）句首出现即生效，弱关键词（`向量 / 全文`）必须紧跟分隔符（`：: ，、。;` 或空格）才算开关；「证据：」这类前缀只用于索取执行计划，会从检索句子里剥掉。这段逻辑有回归表可跑：

```bash
python3 dify/scripts/routing-selftest.py --save   # 结果：evidence/mode-routing-selftest.txt（10 条话术 10 PASS）
```

脚本不复制一份逻辑，而是直接从 `dsl/interview-coach.yml` 里把「模式路由」节点的 `code` 源码抽出来 `exec`，保证测的就是线上那段。

一个必须记住的变量名坑：知识检索节点的输出变量是 **`result`**（源码 `outputs = {"result": ArrayObjectSegment(...)}`），不是 `results`。写成 `results` 时 LLM 不会报错，只会安静地拿到空 context——现象是模型在思考里说"知识库检索通道为空"，全靠工具通道出题，看起来像假数据。复现时如果回答里"知识库命中题数"总是 0，先查这里。

另外三处直接影响"评委看到什么"的细节：

- **思考内容会不会漏进正文**：LLM 节点的 `reasoning_format` 默认是 `tagged`，即把推理过程用分隔符拼在正文里一起吐给前端；本项目显式设成 `separated`，思考走 `reasoning_content` 通道，`answer` 里只有面向候选人的正文。`run-*.json` 的回答全文可以直接检查这一点。
- **温度**：`deepseek-flash` 的 `temperature` 从 0.4 降到 0.25。这个应用的判分要稳定复现（同一份素材、同一个错误答案，两轮结论必须一致），温度高时模型会偶尔把「及格」判成「良好」，也会自作主张改「检索小结」的措辞。多轮演示（`run-two-turns.json`）在 0.25 下第 2 轮仍然给出「不及格 + 逐条对标尺 + 指出常见误区」，说明降温度没有伤到判分粒度。
- **数字不由模型转述**：`took_ms`、`embed_ms`、命中条数这些值，改由「检索小结」代码节点从工具返回的 JSON 里定位取出，回答节点直接追加那一行。这样证据链上的数字与 seekdb 返回值一一对应，不受模型发挥影响；取证脚本 `run-app.mjs` 会独立从 SSE 的节点输出再算一遍（`summary` 字段），两边对得上才算通过。

## 5. DSL 导入的可移植性设计

DSL 里有两个租户内主键：知识检索节点的 `dataset_ids` 和工具节点的 `provider_id`（必须是 `tool_api_providers.id` 这个 UUID，填成工具名会在运行期报 `invalid input syntax for type uuid`）。`scripts/import-dsl.mjs` 在导入前按当前工作区真实值改写这两个字段，因此评委侧的执行顺序是"先建库、先注册工具，再导 DSL"，导入后不需要进节点手工重选。同一脚本还支持 `--app-id`（覆盖已有应用）、`--publish`（取草稿并发布）、`--export`（导出服务器规范 DSL 作为版本对照）。

## 6. 模型与凭据纪律

- LLM：DeepSeek（插件 `langgenius/deepseek` 0.0.26，模型 `deepseek-flash`）。Key 只在使用者本机生效：或后台「模型供应商」手填，或 `DEEPSEEK_API_KEY=… node scripts/setup-models.mjs` 一次性注入；仓库、脚本、日志、导出的 DSL 里都不出现明文。
- Embedding：本机 `dify/embedding`（:8100），Dify 侧以 OpenAI-API-compatible 供应商注册，`api_key` 填占位串（服务端不校验），基址 `http://host.docker.internal:8100/v1`。
- 国内网络前置：marketplace.dify.ai 在容器内直连失败，插件改走 `.difypkg` 本地上传（`plugins/dist/` + `scripts/install-plugins.mjs`）；HuggingFace 换 hf-mirror（`embedding/scripts/fetch-model.mjs`）；Docker Hub 镜像需按个人环境配置加速器。
- 竞赛要求的"配置项均使用占位值"落实为：管理员 `admin@seekdb.local / Seekdb2026Demo`、seekdb 口令 `difyai123456`、应用 API Key 只在 `make-app-key.mjs` 输出一次且不入库、一次性隧道 URL 一律不进仓库。

## 7. 消融实验与结论

`scripts/ablation.mjs` 用 14 条按「术语 / 口语改写 / 数字参数」标注的查询，对同一张表跑三种模式（top_k=5，recall=20），以"正确素材的题面子串"预先定义 ground truth，统计 Top1、Top5 内命中与 MRR（结果：`evidence/retrieval-ablation.md`）。

| 模式 | Top1 | Top5 内 | MRR | 平均耗时（预热后 3 遍中位数） |
| ---- | ---- | ------- | --- | ---------------------------- |
| hybrid | 12/14 | 14/14 | 0.929 | 9 ms |
| vector | 11/14 | 13/14 | 0.857 | 9 ms |
| fts | 12/14 | 14/14 | 0.895 | 9 ms |

结论：单通道各有结构性盲区——纯向量对数字/参数名不敏感（`TIME_WAIT 为什么要等 2MSL` 把 Nagle 排在四次挥手之前），纯全文对口语化改写不召回（`消息队列怎么保证同一条消息不被处理两遍` 只排到第 3）；混合的价值体现在 MRR 最高且 Top5 内 14/14 全召回，两路互为替补。三种模式在 162 块、单分片本地 seekdb 上耗时同为 10ms 量级（预热后），也就是说**混合检索在这里几乎零代价**；真正的耗时全在 LLM（单轮 3-7s）。耗时列不给模式分优劣——本机不加预热时第一遍能比后面慢 5-10 倍，脚本因此先跑一遍预热、再连测 3 遍取中位数，每遍数值都在 `evidence/retrieval-ablation.md` 里列全。

## 8. 已知边界与后续

- 本地 512 维小模型的语义上限低于线上大模型，个别近义题会互相抢位（消融里 hybrid 未进 Top1 的两条属于此类，正确素材同时含"死信/热 key"等更宽的词，是题库覆盖问题而非通路问题）。
- Dify 的混合融合细节（权重、去重）由框架内部完成，本项目不依赖其算法，而是另实现一条可解释的 RRF 通路作为对照；若评委只想验证"真的在用 seekdb"，通路 A 的 DDL + `SHOW INDEX` + 节点追踪已经足够。
- 会话级难度自适应目前靠提示词与素材「难度」字段，未落库为候选人画像；下一步可把每轮判分结果写回 seekdb（同一实例即可承担记忆存储），形成"练—评—追"闭环。
- 语料为原创整理，覆盖后端校招/社招常见方向；换主题只需按 `docs/知识库构建说明.md` 替换 `kb/*.md`，其余流程不变。
